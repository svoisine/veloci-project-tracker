Architecture

Veloci Project Tracker · Architecture

VPT is a local, single-user, full-stack app that turns a Google Sheet into a live project dashboard. This document describes how it's built: the topology, the request flow, the module layout, and the security and failure models.

01 Overview

The Google Sheet is the source of truth. VPT is a read/write window onto it that computes a prioritized view — progress, what's ready to work on, what's blocked — and lets you edit task status and notes. It runs entirely on your own machine: a Node/Express backend plus a React UI. No hosting, no login, no accounts, no database, and no third party receives your data.

Why there's a backend at all: a browser tab cannot safely hold a Google service-account key (it would be exposed in page source and network traffic). A small local server holds the key on disk and talks to Google; the browser only ever calls /api/… on that local server. That single constraint is why VPT is full-stack rather than a static page.

04 Module layout

The codebase is organized so each file owns one job. The server entry point is a listener and nothing else; routing, handlers, HTTP envelopes, sheet I/O, compute, and config storage are separate concerns.

Structural guarantee: because config/ imports nothing from sheets/, "deleting a project can never touch your Google data" isn't a promise to trust — it's impossible in the code. A shared contract.js holds the validation rules (id pattern, field caps, default ranges) used by both tiers, so the browser and server can't drift; the server remains the authority and re-validates everything.

06 The write path

  • Single-cell writes only. One POST /api/step changes one cell (status, notes, or blocked_by) — never a row or range.
  • Closed field whitelist, column located by header name, so reordering sheet columns can't misdirect a write.
  • Stale guard. Before writing, VPT re-reads the target cell; if it changed since the page loaded, the write is refused and the UI refreshes to the sheet's truth rather than overwriting.
  • Writes require live data — VPT won't locate a row from a stale cache, so it refuses to write while offline. A rejected notes save preserves the user's typed text.
Known limit: the stale guard is a narrow re-read window, not a transaction — two writers saving the same cell in the same instant can still interleave. The realistic case (an edit made minutes ago elsewhere) is covered. Full optimistic concurrency is out of scope for a single-user tool.

Notes activity feed

Notes on a shared sheet are useless if written once and never seen. VPT surfaces them in a filterable panel grouped by the status of the step each note sits on, flagging notes that are new or changed since this machine last marked them seen. The Sheet exposes no change history to read, so "new since last time" is not discovered but remembered: a local two-slot snapshot (~/.vpt/vpt_notes_snapshot_<id>.json) keeps previous, the last state acknowledged, and current, the last state shown, and the feed diffs the sheet against previous.

Only the explicit Mark all seen action moves that baseline — reopening the project or restarting the server does not, so unread notes survive the app being closed overnight. The feature is read-only by construction: no column is added, no schema changes, no authorship is recorded (VPT has no user identity to attribute a note to), and the only thing written is that local file — the per-step editor remains the sole write path for a note. Because the diff is local, the feed is just as correct on a cached pull as a live one. The baseline is per machine, so two people on one sheet each track their own "new".

Rendering is capped: at most 300 cards enter the DOM after filtering, with a "showing the first 300 of N matching notes" line and the filters to narrow with. A 20,000-row tracker yields roughly 10,000 feed items, and rendering them all froze the tab. The cap is on rendering only — the counts, the header badge and the diff itself always run over the full set.

07 Security model

  • The key never reaches the browser. It's read server-side from disk; that's the reason the backend exists.
  • The key is a service-account identity, not a per-sheet password. Access is granted by sharing a sheet with its client_email; revoke by unsharing, rotate by recreating the key.
  • Path traversal is blocked. Project ids are validated (they become filenames); a filename always wins over an id field inside a file; template downloads use a closed name→file map.
  • The server is local and unauthenticated — acceptable because it binds to your machine. The single load-bearing assumption is: don't expose it to a network.
  • Secrets never enter git — .gitignore excludes keys, real project configs, and caches.

The sheet is authoritative for content; local files for configuration. They own different things, so they never conflict — which is why two machines "sync" for free (they read the same sheet) and why deleting a project locally can't affect the sheet.

09 Failure model

Every /api route returns 200 with a JSON envelope ({ok, reason, …}) — bad input, missing key, dead network, and malformed config all become described states the UI renders, never an error status. Network calls time out and fall back to cache. A React error boundary backstops render-time failures with a Reload action.

Three data states the UI distinguishes: ● live · ⚠ cached (editing disabled) · ✗ no data (with a hint).

Verified, not assumed. The failure and input-handling behavior was audited by inducing real conditions — malformed configs written to disk, hostile sheet data through the real compute, abusive request bodies, corrupt keys, unwritable directories, the backend killed under a live page. Circular prerequisite chains cannot hang the compute; day-boundary math is exact across timezones and DST; atomic writes leave no partial files.

10 Known limitations

  • Single-user by design. The security model rests on the server being local; it is not built to be exposed to a network.
  • Not responsive below ~1100px. The layout has minimum column widths; small viewports scroll horizontally. Responsiveness is a deferred feature.
  • Windows-first launcher. npm start is cross-platform; the double-click launcher and login-at-startup are Windows.
  • No committed test suite yet. Behavior has been verified via extensive throwaway harnesses rather than tests kept in the repo; the natural first permanent tests are the pure functions in brief/, notes/ and config/.
  • Very large sheets slow the dashboard. Several core lists — in progress, the ready lanes, open KNs — are uncapped, so a tracker in the tens of thousands of rows renders sluggishly. Only pull-ahead, implicit blockers and the notes feed are capped today; extending the same treatment to the remaining lists is a known backlog item, not a notes-feed issue.
  • Stale-write window as described in §06.
